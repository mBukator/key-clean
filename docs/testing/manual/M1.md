# M1 manual test - keyboard lock, emergency unlock, safety limits

Milestone: M1 (§62). Run by Max, never by Claude. Fill in every **Result** cell, then send the
summary table at the end back to Claude.

There are two targets. Run each step against both unless it says otherwise:

| Target         | How to start (from `D:\Projects\personal\key-clean`)                                                          | Process name | Lock length                                            |
| -------------- | ------------------------------------------------------------------------------------------------------------- | ------------ | ------------------------------------------------------ |
| **lock_smoke** | Build once: `cargo build -p keyclean-win --example lock_smoke`. Run: `.\target\debug\examples\lock_smoke.exe` | `lock_smoke` | 15 s after a 3 s countdown                             |
| **Shell**      | `bun tauri dev` (leave this terminal open; it prints session events)                                          | `keyclean`   | 10 s, starts when you click **Lock keyboard for 10 s** |

Both are debug builds, so every lock is capped at 15 s with a 20 s hard deadline ("DEV CAP"). Nothing
in this test can lock for longer than 20 s.

Where to read the outcome:

- **lock_smoke** prints `state: ...`, `notice: ...` and finally `Unlocked. End reason: <reason>` in
  its console, then exits.
- **Shell** shows "Last lock ended: ..." in the window, and the `bun tauri dev` terminal prints
  `[keyclean] session ended: <reason>` plus any `[keyclean] notice: ...` lines. The shell has no
  Unlock button.

End reasons as printed: `Timeout`, `Emergency`, `HardDeadline`, `UserRequest`, `EngineError`,
`SystemTransition(Suspend)`, `SystemTransition(EndSession)`, `SystemTransition(SessionLock)`,
`SystemTransition(SessionDisconnect)`.

## Part A - automated run (do this first)

The harness `crates/keyclean-e2e` (ADR 0008) runs most of this script by itself in about 2 minutes,
using synthesized keys. It locks your keyboard several times: keep your hands off the keyboard until it
prints the results. The mouse is never locked, the real Ctrl+Alt+K always works, and an outside
watchdog kills the harness after 6 minutes.

1. Close any running KeyClean (`bun tauri dev` or `keyclean.exe`) and pause keyboard tools such as
   AutoHotkey or PowerToys Keyboard Manager (they can swallow the synthesized keys; the harness
   detects this and stops with exit code 2).
2. Build both targets:

    ```powershell
    cargo build -p keyclean-win --example lock_smoke
    bun run build; cargo build -p keyclean
    ```

3. Run it, then click into an empty Notepad window during the 5 s countdown:

    ```powershell
    cargo run -p keyclean-e2e
    # optional: add `-- --session-lock` to also test Win+L-style workstation lock (sign back in after)
    ```

4. Send Claude the printed table (also saved as `target\debug\e2e-report.md`).

| Harness check | Covers step       | What it proves                                                                       |
| ------------- | ----------------- | ------------------------------------------------------------------------------------ |
| S1            | 1 (keyboard list) | The engine lists at least one keyboard                                               |
| S2            | 2, 10             | Keys are blocked; Ctrl+Alt+K unlocks within 500 ms; nothing leaks or sticks          |
| S3            | 3                 | Ctrl+Alt+K held with auto-repeat for 3 s: nothing reaches Windows                    |
| S4            | 4                 | A 3 s lock ends with `Timeout` on time                                               |
| S5            | 9                 | Keys held at lock start: repeats blocked, releases pass, nothing sticks              |
| S6            | 5 (synthesized)   | Win, Alt+Tab, Ctrl+Esc, Win+X, volume, Ctrl+Shift+Esc, Win+G never get past KeyClean |
| S7            | 15                | LCtrl+RAlt+K (what AltGr sends) counts as the chord                                  |
| S8            | 7 (logic)         | Presses whose releases never arrive end the drain with `DrainTimedOut`               |
| S9            | 8 (lock_smoke)    | Killing lock_smoke mid-lock gives input back immediately                             |
| S10, S11, S12 | 8 (Shell), 13, 14 | Killing the app or closing its window mid-lock releases input; a 2nd instance exits  |
| S13 (opt-in)  | 6                 | Locking the workstation ends the session with `SystemTransition(SessionLock)`        |

If a check fails, run the matching step below by hand and send both results. To re-run only some
checks: `cargo run -p keyclean-e2e -- --only S11` (comma-separated IDs). The app checks save the app's
session log (never keys) as `target\debug\e2e-S10-app.log` and so on.

The full step list below stays as the reference for Part B and for re-running anything the harness
failed.

## The no-keyboard rule

While a lock is active you never need the keyboard to get out. Every step ends by itself (the timer),
by the mouse, or by a PowerShell command you type and start **before** locking. Where a step asks you to
press keys during a lock, those keys are the thing being tested, not the way out.

## Preconditions

- [ ] Save your work in every open app. Close nothing important, but expect apps to lose focus.
- [ ] Know your escape hatches: **Ctrl+Alt+Del always works** (it is handled by Windows, not by any
      app), and holding the **power button** always works. You won't need either, but they exist.
- [ ] Mouse or touchpad connected and working (KeyClean M1 never locks it).
- [ ] Open **Notepad** (type `notepad` in a PowerShell window and press Enter). It is the "did a
      key get through?" detector.
- [ ] Open the **On-Screen Keyboard** (type `osk` and press Enter, or Start → All apps → Accessibility
      → On-Screen Keyboard). It highlights keys Windows thinks are held down, so a stuck Shift, Ctrl,
      Alt or Win shows up as a lit key. Only _look_ at it, don't click it, except in step 17.
- [ ] Build `lock_smoke` once (command above) and check `bun tauri dev` starts.

"Stuck-key check" below means: look at the On-Screen Keyboard. **Pass** = no modifier key is lit. Then
click into Notepad and type `abc` - it must appear as lowercase `abc`.

## Step 3 - Holding the chord after unlock (auto-repeat)

1. Start a lock and click into Notepad.
2. Within the first 5 seconds of the lock, press **Ctrl+Alt+K** and **keep all three held for 3 seconds** (count slowly), then release.
3. Look at Notepad, then do the stuck-key check.

**Expected:** the lock ends (`Emergency`). Nothing is typed in Notepad while the keys are held or
after release, no shortcut fires, no lit modifiers.

> How it works: after the lock ends, the engine keeps blocking the keys you were already holding for as
> long as they keep auto-repeating (up to 30 s), and gives up 2 s after they go quiet. It never blocks
> past the hard deadline (20 s after the lock started in these debug builds) - there everything is
> released on purpose. Pressing the chord early and holding for 3 s, or even 10 s, should type nothing. If `k` characters do appear, record roughly when they started -
> that's a real finding, not a test mistake.

## Step 7 - Ctrl+Alt+Del during a lock (documented escape hatch)

Run this on its own lock.

1. Start a lock and click into Notepad.
2. Press **Ctrl+Alt+Del**. The Windows security screen should appear.
3. Click **Cancel** with the mouse.
4. Back on the desktop, click into Notepad and type `abc` (avoid `k`: Windows never delivered the Ctrl
   and Alt releases, so KeyClean still counts them as held and `k` would end the lock as `Emergency`).
   Note whether the letters appear.
5. Wait for the lock to end by itself. Note the end reason and any `notice:` line.
6. Stuck-key check.

**Expected:** the security screen appears (it always does). After Cancel, record what happens. Our
prediction: the lock continues until its timer, ends with `Timeout`, and prints
`notice: DrainTimedOut` (Windows never delivered the Ctrl, Alt and Del releases to the hook, so the engine
waits 2 s and then releases anyway). No lit modifiers at the end.

## Step 8 - Forced kill mid-lock (pre-armed PowerShell)

**lock_smoke.** In a PowerShell window at the repo root, type this and press Enter. It starts
lock_smoke in its own console, which locks after 3 s, and kills it 4 s into the lock:

```powershell
Start-Process .\target\debug\examples\lock_smoke.exe; Start-Sleep 7; Stop-Process -Name lock_smoke -Force
```

Click into Notepad right away. After the kill (the lock_smoke console disappears), type `abc` and do the
stuck-key check.

**Shell.** With `bun tauri dev` running, open a **second** PowerShell window, type this and press Enter,
then click the **Lock** button within 3 seconds and click into Notepad:

```powershell
Start-Sleep 8; Stop-Process -Name keyclean -Force
```

The window disappears about 5 s into the lock (the dev terminal reports the process exited). Type `abc`
and do the stuck-key check.

**Expected:** the moment the process dies, the keyboard works (Windows removes the hook of a dead
process). `abc` appears, no lit modifiers.
