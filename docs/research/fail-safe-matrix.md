# Fail-safe matrix

What happens to a lock (keyboard, and from M5 the mouse too) when something goes wrong, and how we know. Covers every §47 case plus
the extra cases found in Phase 0 research (`phase-0-windows-input.md`).

"How verified" is one of:

- a unit test name in `keyclean-core` / `keyclean-win` (pure logic only; no test installs a hook);
- an M1 manual step (`docs/testing/manual/M1.md`, "M1 step N");
- "M3 step N" - `docs/testing/manual/M3.md`; "harness Sn" - `cargo run -p keyclean-e2e` (ADR 0008);
- "code review" - the mechanism exists but has no automated or manual test yet.

The four independent exits from every lock (invariant 1) are: session timer, hard deadline (hook check
plus watchdog), emergency chord Ctrl+Alt+K, and Windows removing the hook when the process dies.

## §47 failure cases

| Failure case              | Mechanism                                                                                                                                                                                                                                                                                                    | Expected result                                                                                                                           | How verified                                                                                                                                                                 |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Permission failure        | `SetWindowsHookExW` fails → engine reports `EngineError::HookInstall`, clears hook state, session ends with `EngineError`.                                                                                                                                                                                   | Nothing is locked. Plain-language error "Windows didn't allow KeyClean to lock the keyboard. Nothing was locked." with technical details. | Harness S18 (install failure forced by the test kit)                                                                                                                         |
| Device disconnected       | One global hook locks every keyboard (ADR 0004), so a disconnect changes nothing for the lock. During a session the engine's Raw Input registration (`RIDEV_DEVNOTIFY`) delivers `WM_INPUT_DEVICE_CHANGE`; a removal of a keyboard known at lock start emits `DeviceChanged(Removed)` (no names) (ADR 0010). | Lock continues; other keyboards stay blocked; the window says "Keyboard disconnected." and re-lists keyboards.                            | M3 step 6                                                                                                                                                                    |
| Device reconnect          | Same global hook: a reconnected or new keyboard is blocked like any other (ADR 0004, ADR 0010 replace §26's "don't lock new devices"). An arrival not known at lock start emits `DeviceChanged(Arrived)`; replayed arrivals of known keyboards are ignored.                                                  | Reconnected keyboard is blocked during the lock; the window says "A keyboard was connected. It is locked too." and the list refreshes.    | M3 step 6                                                                                                                                                                    |
| Application crash         | `panic = "abort"` in dev and release → any panic ends the process → Windows removes the hook. Native crashes end the process the same way.                                                                                                                                                                   | Input released at once.                                                                                                                   | M1 step 8 (process death); code review (`Cargo.toml` profiles)                                                                                                               |
| Forced termination        | Windows removes every hook of a process that exits, however it exits (Task Manager, `Stop-Process -Force`). [docs] The hook lives in the engine process (ADR 0009); `Stop-Process -Name keyclean` ends both processes.                                                                                       | Keyboard works the moment the process dies; nothing stuck.                                                                                | M1 step 8 (both targets); harness S9, S10                                                                                                                                    |
| Windows shutdown / logoff | Hidden top-level window gets `WM_QUERYENDSESSION` → returns TRUE (never blocks) and unhooks immediately without drain; also `WM_ENDSESSION` and `WTS_SESSION_LOGOFF`. End reason `SystemTransition(EndSession)`.                                                                                             | Shutdown is never delayed by KeyClean; input released before the session ends.                                                            | M3 steps 1, 2 (logoff itself: optional M3 step 3, skipped; same `WM_QUERYENDSESSION` handler)                                                                                |
| Windows sleep             | `RegisterSuspendResumeNotification` → `PBT_APMSUSPEND` → unhook immediately. Engine is idle after resume; no lock resumes.                                                                                                                                                                                   | Idle after wake; end reason `SystemTransition(Suspend)` (or `SessionLock` if Windows locks first).                                        | M1 step 12; M3 step 4 (S3 standby, 2026-10-04: ended as `SessionLock`, Windows locked first)                                                                                 |
| Windows restart           | Same as shutdown. No lock state is written anywhere (no files, registry, settings), so nothing survives a restart.                                                                                                                                                                                           | App starts idle after restart.                                                                                                            | M3 step 2; code review (no persistence code exists)                                                                                                                          |
| Timer failure             | Session timer (`SetTimer`) failing to arm ends the session with `EngineError`. If it never fires, the hard deadline still ends the lock twice over: hook check on every event and the watchdog thread.                                                                                                       | Lock ends no later than the hard deadline.                                                                                                | `policy` tests (`hard_deadline_is_never_before_session`); `session` tests (`expiry_edges`, `hard_deadline_wins_after_a_long_gap`); harness S16 (no session timer); M1 step 4 |

## Additional cases

| Failure case                                                                               | Mechanism                                                                                                                                                                                                                                                                                                                                                                                                                                    | Expected result                                                                                                                                                                                                                               | How verified                                                                                                                                                                                                                                                                       |
| ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Panic anywhere                                                                             | `panic = "abort"` → process exit → Windows frees the hook. Inside the hook, `catch_unwind` returns Pass as a defence for unwind builds (invariant 10).                                                                                                                                                                                                                                                                                       | Input released.                                                                                                                                                                                                                               | Code review; M1 step 8 covers process death                                                                                                                                                                                                                                        |
| Silent hook removal (`LowLevelHooksTimeout`)                                               | Windows removes or skips a slow hook without telling us. The callback is O(1) to avoid this. During a session a Raw Input sink (`RIDEV_INPUTSINK`) sees keystrokes too; 250 ms after a `WM_INPUT` the engine checks that the hook ran around then (`liveness::hook_alive`). If not and the focused window isn't elevated, the session ends with `error.hook_lost` (ADR 0010). If unhooking then fails, the engine logs `HookAlreadyRemoved`. | Lock ends within about 250 ms of the first key that gets through, and the user is told.                                                                                                                                                       | `liveness` tests; harness S17 (hook removed by the test kit), S20 (opt-in, real timeout)                                                                                                                                                                                           |
| Engine thread hang                                                                         | Watchdog thread at the hard deadline sets the hook to Passthrough (every event passes), posts `WM_WATCHDOG_EXPIRED`, and ends the process with `TerminateProcess` (exit code `0x4B43`) if the engine doesn't acknowledge within 1 s; `abort()` went through Windows Error Reporting, which held the process (and its hook) about 5 s. A hung thread also trips `LowLevelHooksTimeout`.                                                       | Input released by the hard deadline at the latest, plus at most 1 s.                                                                                                                                                                          | Harness S19 (engine thread hung in a child process; watchdog ends it about 14 s in)                                                                                                                                                                                                |
| Webview crash or close                                                                     | The engine runs in its own process and owns the lock; the webview only sends requests (invariant 3). Closing the main window exits the app; `RunEvent::Exit` drops the engine client, which sends `shutdown` and the engine unhooks (`UserRequest`).                                                                                                                                                                                         | Webview problems never extend a lock; closing the window exits and unlocks.                                                                                                                                                                   | M1 step 13; harness S11                                                                                                                                                                                                                                                            |
| Hidden engine window gets `WM_CLOSE` / destroyed                                           | `WM_CLOSE` is ignored. If the window is destroyed anyway, the session ends and the engine stops (input released).                                                                                                                                                                                                                                                                                                                            | No way to strand a hook by closing the hidden window.                                                                                                                                                                                         | Code review (see note below)                                                                                                                                                                                                                                                       |
| `WM_CLOSE` sent to every app window (e.g. `taskkill` without `/F` [assumption])            | The engine's own window ignores it. tao's event target window and the single-instance window used to be destroyed by it, which hung the UI. `keyclean_win::guard_helper_windows` (called in `setup`) subclasses them so `WM_CLOSE` exits the app normally; the engine then ends the lock (`UserRequest`) and exits.                                                                                                                          | App exits cleanly; input released; no `keyclean.exe` left.                                                                                                                                                                                    | Harness S23; M3 step 9                                                                                                                                                                                                                                                             |
| Workstation lock / Win+L / session switch                                                  | `WTSRegisterSessionNotification` → `WTS_SESSION_LOCK`, `WTS_CONSOLE_DISCONNECT`, `WTS_REMOTE_DISCONNECT` → unhook immediately. Win+L itself can't be blocked.                                                                                                                                                                                                                                                                                | Windows locks; KeyClean ends with `SystemTransition(SessionLock)` or `SessionDisconnect`.                                                                                                                                                     | M1 step 6                                                                                                                                                                                                                                                                          |
| Ctrl+Alt+Del mid-lock                                                                      | Can't be blocked (Secure Attention Sequence). The releases happen on the secure desktop, so the hook never sees them; at session end the drain waits 2 s, then unhooks (`DrainTimedOut` notice).                                                                                                                                                                                                                                             | Security screen appears; the lock ends normally; nothing stuck.                                                                                                                                                                               | `keystate` test `ctrl_alt_del_mid_lock_never_drains`; M1 step 7                                                                                                                                                                                                                    |
| Keys held at lock start                                                                    | Engine snapshots held keys into `os_down` (via `GetAsyncKeyState`, before anything is blocked). Their releases pass during the lock, so Windows sees each key come back up.                                                                                                                                                                                                                                                                  | No stuck Shift/Ctrl/Alt/Win after unlock.                                                                                                                                                                                                     | `keystate` tests `key_held_at_lock_start_repeats_then_releases`, `key_pressed_during_arming_is_tracked_without_snapshot`; M1 step 9                                                                                                                                                |
| Chord auto-repeat after unlock                                                             | After Ctrl+Alt+K the hook stays in Draining: repeats and releases of blocked presses stay blocked until all are released. The drain ends 2 s after blocked keys go quiet (`DRAIN_IDLE_TIMEOUT`), 30 s at most (`DRAIN_MAX`) and never past the hard deadline, where the hook switches to passthrough; auto-repeat keeps it alive.                                                                                                            | Nothing typed while the chord is held, up to 30 s or the hard deadline, whichever comes first.                                                                                                                                                | `keystate` test `chord_then_auto_repeat_during_drain_reaches_nothing`; `policy` tests `auto_repeat_keeps_the_drain_alive`, `drain_is_capped_even_while_repeating`; M1 step 3                                                                                                       |
| Elevated window focused                                                                    | UIPI may stop a normal-privilege hook from seeing input meant for an admin window. KeyClean runs `asInvoker` (ADR 0005). If the liveness check sees keys the hook missed while an elevated window has focus, the lock stays on and the window warns once (ADR 0010).                                                                                                                                                                         | Measured: M1 (2026-10-02, engine in the app process) got through; M3 (2026-10-04, engine process) **blocked**. If keys do get through, the window warns "Typing reaches administrator windows during a lock." and other windows stay blocked. | M1 step 11; M3 step 7                                                                                                                                                                                                                                                              |
| Injected input (OSK, SendInput, remappers)                                                 | Blocked by the same rules as physical input; the hook doesn't check `LLKHF_INJECTED` (ADR 0007).                                                                                                                                                                                                                                                                                                                                             | On-Screen Keyboard clicks do nothing during a lock.                                                                                                                                                                                           | M1 step 17                                                                                                                                                                                                                                                                         |
| Second instance                                                                            | `tauri-plugin-single-instance`, registered first: a second launch focuses the existing window and exits. Only the app starts an engine process, and `--engine` is dispatched before Tauri starts. `Engine::start` also refuses a second engine in one process (`AlreadyRunning`).                                                                                                                                                            | One app, one engine process, one hook, ever. A running instance is two `keyclean.exe` processes.                                                                                                                                              | M1 step 14; harness S12                                                                                                                                                                                                                                                            |
| Engine process killed or crashes (ADR 0009)                                                | Windows removes the hook of the dead engine process. The app sees stdout close and reports `EngineError::EngineProcess`, plus `SessionEnded(EngineError)` if a lock was active, then starts a new idle engine - at most 3 times in 5 minutes (ADR 0011).                                                                                                                                                                                     | Keyboard works the moment the engine process dies; the app says the engine was restarted and nothing is locked.                                                                                                                               | `restart` tests; `bridge` tests; harness S21; M3 step 8                                                                                                                                                                                                                            |
| App killed or crashes while the engine runs (ADR 0009)                                     | The engine process exits when its stdin reaches EOF (orderly unlock), when its parent-process watcher (`OpenProcess(SYNCHRONIZE)` + `WaitForSingleObject`) sees the app exit, or when a stdout write fails. Windows then removes its hook. If the app process can't be opened for watching, EOF alone is relied on.                                                                                                                          | Keyboard works right after the app dies; no `keyclean.exe` is left behind.                                                                                                                                                                    | Harness S10 (no `keyclean.exe` within 5 s); M1 step 8 (Shell)                                                                                                                                                                                                                      |
| App window focused during a lock                                                           | Windows intermittently skips a `WH_KEYBOARD_LL` hook while a WebView2 window of the hook's own process has focus (tauri-apps/tauri#13919, `webview-focus-hook.md`). The hook now lives in the engine process, which has no WebView.                                                                                                                                                                                                          | Keys stay blocked and Ctrl+Alt+K works with the KeyClean window focused.                                                                                                                                                                      | Harness S14; M1 steps F1, F3                                                                                                                                                                                                                                                       |
| Debug build                                                                                | `keyclean-win` forces `SafetyProfile::Dev` under `cfg!(debug_assertions)`: session ≤ 15 s, hard deadline ≤ 20 s, "DEV CAP" shown. `lock_smoke` clamps to the dev caps even in `--release`.                                                                                                                                                                                                                                                   | No debug build can lock longer than 20 s.                                                                                                                                                                                                     | `policy` tests `dev_caps_session_and_hard_deadline`, `dev_ten_second_session`; M1 steps 1, 4                                                                                                                                                                                       |
| Raw Input registration at idle                                                             | The engine registers keyboard Raw Input (and mouse Raw Input in a mouse lock) only between installing and removing the hooks, and removes the same set in `finish()` and at engine shutdown (invariant 4, ADR 0010, ADR 0013).                                                                                                                                                                                                               | Idle KeyClean has no hook and no input registration.                                                                                                                                                                                          | Harness S22 (also after a mouse lock)                                                                                                                                                                                                                                              |
| Xbox Game Bar open during a lock (Win+G)                                                   | Win+G opens the Game Bar even during a lock (it acts outside the hook). While the overlay is open, Windows delivers no Raw Input to KeyClean, so the lost-hook check has nothing to compare (ADR 0010, known limitation).                                                                                                                                                                                                                    | Lock keeps blocking and ends by its usual exits; a hook lost while the overlay is open isn't reported until it closes.                                                                                                                        | Harness S25 (opt-in); M3 step 11                                                                                                                                                                                                                                                   |
| Hard deadline                                                                              | `min(max_lock, session + 10 s)`, max-lock clamped to an absolute 60 min (ADR 0006). Enforced twice: hook compares QPC ticks to an atomic deadline on every event (a lock moves to Draining; a drain still running moves to Passthrough), and the watchdog thread fires on its own.                                                                                                                                                           | Lock ends at the hard deadline even if the timer, the chord, and one of the two enforcers fail.                                                                                                                                               | `policy` tests `release_hard_deadline_is_session_plus_grace`, `release_hard_deadline_never_exceeds_max_lock`, `max_lock_setting_is_clamped_to_absolute_ceiling`; `session` test `hard_deadline_wins_after_a_long_gap`. Not reachable by hand in M1 (the timer always fires first). |
| Stale message from an earlier session                                                      | Hook and watchdog messages carry a session generation number; the engine ignores messages from an older generation (ADR 0006).                                                                                                                                                                                                                                                                                                               | A late message can't end or alter a newer lock.                                                                                                                                                                                               | Code review                                                                                                                                                                                                                                                                        |
| Clock change / timer drift                                                                 | Deadlines use QPC (`Instant`), which ignores wall-clock changes; the watchdog compares `Instant`s. The session timer re-arms if it fires early; a late fire is bounded by the hard deadline.                                                                                                                                                                                                                                                 | Changing the system clock doesn't change the lock length.                                                                                                                                                                                     | M3 step 5 (clock jump ±1 h); M2 steps 6-8, harness S15 (accuracy); M3 step 10 (optional, under load)                                                                                                                                                                               |
| Mouse lock exits (ADR 0013)                                                                | Same four exits as the keyboard. The keyboard hook, which detects Ctrl+Alt+K, is installed for every lock, also a mouse-only one. Both hooks check the hard deadline on every event (a mouse-only lock with nobody typing still ends), and the watchdog fires on its own. Windows removes both hooks when the process dies.                                                                                                                  | Mouse, touchpad and keyboard work again after every exit.                                                                                                                                                                                     | Harness S26 (chord), S28 (timer), S29 (hard deadline, mouse events only), S30 (kill); M5 steps 4-6                                                                                                                                                                                 |
| Chord in a mouse-only lock                                                                 | The keyboard hook lets keys through and swallows only the key that completes Ctrl+Alt+K, plus its repeats and release (`keystate::keyboard_phase`).                                                                                                                                                                                                                                                                                          | Ctrl and Alt reach the focused app, K doesn't; nothing stuck.                                                                                                                                                                                 | `keystate` tests `mouse_only_*`; harness S27; M5 step 4                                                                                                                                                                                                                            |
| Mouse button held when a lock ends                                                         | A blocked press swallows its release; any other release passes; the drain waits for held buttons as for keys (`mouse::ButtonTracker`). Nothing is read from system state.                                                                                                                                                                                                                                                                    | No button stuck down after unlock.                                                                                                                                                                                                            | `mouse` tests; harness S26 (release swallowed); M5 step 5                                                                                                                                                                                                                          |
| Mouse hook install fails                                                                   | The keyboard hook went in first; it is removed again and the session ends with `error.hook_install`. Both hooks pass everything while arming.                                                                                                                                                                                                                                                                                                | Nothing is locked; the user is told.                                                                                                                                                                                                          | Harness S32 (failure forced by the test kit)                                                                                                                                                                                                                                       |
| Silent mouse hook removal                                                                  | During a mouse lock, mouse Raw Input is registered too; the engine reads only each `WM_INPUT` header (device type) and runs the ADR 0010 check against the mouse hook's last call. Input to an elevated window under the cursor warns instead (ADR 0013).                                                                                                                                                                                    | Lock ends with `error.mouse_hook_lost` about 250 ms after the first mouse input that gets through.                                                                                                                                            | Harness S31; `liveness` tests                                                                                                                                                                                                                                                      |
| Touchpad gestures during a mouse lock                                                      | Precision touchpads are Limited (ADR 0004). Pointer movement, taps and clicks reach the mouse hook and are blocked; two-finger scroll, pinch and three- and four-finger swipes never pass the hook.                                                                                                                                                                                                                                          | Gestures still scroll, zoom, open Task View and switch desktops; the touchpad note says so; no lock ends early because of them.                                                                                                               | M5 steps 2 (`--mouse-diag`: 0 misses) and 7                                                                                                                                                                                                                                        |
| Injected mouse input                                                                       | Blocked like physical input; the mouse hook ignores `LLMHF_INJECTED` (ADR 0007, ADR 0013).                                                                                                                                                                                                                                                                                                                                                   | Remote-control and scripted mouse input do nothing during a mouse lock.                                                                                                                                                                       | Harness S26 (all probes are injected)                                                                                                                                                                                                                                              |
| Overlay doesn't confirm it is visible within 2 s (slow WebView2, page failed to load)      | The app shows the overlay first and asks the engine to lock only after the page confirms (`overlay_ready`), within a 2 s budget counted in Rust from the request. A late or stale confirmation never locks. The window is then destroyed (ADR 0014).                                                                                                                                                                                         | Nothing is locked. "The lock screen didn't appear in time, so nothing was locked." with technical details.                                                                                                                                    | Harness S36 (`no-ack` fault); `keyclean-core::overlay` unit tests                                                                                                                                                                                                                  |
| A lock engaging before the overlay is visible (regression)                                 | `overlay::lock` requests the lock only after the confirmation, holding the overlay state so a window closing at that moment either prevents the lock or ends it right after.                                                                                                                                                                                                                                                                 | Never locked without a visible overlay (invariant 11).                                                                                                                                                                                        | Harness S34 (overlay polled every 5 ms against the first blocked probe)                                                                                                                                                                                                            |
