# ADR 0016 - System tray and the window lifecycle

- Status: Accepted, 2026-10-12
- Deciders: Max (M8 plan approved 2026-10-11; the points the plan didn't settle confirmed
  2026-10-12 after the M8 manual test: the dashboard subclass (a bare `WM_CLOSE` exits), the
  status text "Something went wrong" (planned: "Couldn't lock"), the Problem state also covering
  errors during a lock until the next lock, one amber locked icon for both taskbars, following the
  scale through `WM_DPICHANGED` too, the harness watchdog at 15 min and the debug-only
  `KEYCLEAN_E2E_AUTOLOCK_GAP_MS`)
- Related: M8; §8-§9, §16, §27, §29-§31, §46, §60; invariants 3, 4, 11, 12; ADR 0001 (idle cost),
  0009 (engine process), 0012 (idle device watch, amended here), 0014 (overlay, amended here),
  0015 (dashboard); `src-tauri/src/{tray,dashboard,lib,overlay,bridge}.rs`,
  `crates/keyclean-win/src/{close_guard,taskbar,raw_input}.rs`, `assets/tray/`,
  `docs/research/m8-tray.md`.

## Context

§27 asks KeyClean to run from the system tray, and ADR 0001 set the idle-cost criterion with the
dashboard "closed to tray (webview destroyed)". Until M8, closing the main window exited the app,
and the main window existed from launch to exit.

While checking idle cost, M8 found that tao registers the app process for Raw Input from every
mouse and keyboard when its event loop starts (`DeviceEventFilter::Unfocused`, tao 0.37.1
`event_loop.rs`). With a KeyClean window focused, the app received `WM_INPUT` for each key; tao
turned it into device events that Tauri dropped. Nothing was stored, but invariant 4 says KeyClean
sees no input at idle, and ADR 0012 claimed the app registers none. Harness S22 missed it because
Raw Input registrations are per process and S22 checks the engine in the harness's own process.

## Decision

### No Raw Input in the app process

`tauri::Builder::device_event_filter(DeviceEventFilter::Always)` makes tao remove its registration
(`RIDEV_REMOVE`) before `setup` runs [docs: tauri 2.12.1 `Builder::build`]. The app logs its own
registration count at startup, and the harness asserts it is 0. The engine process keeps its own
registration, during a lock only (ADR 0010). ADR 0012's claim now holds.

### Windows

- **The dashboard is built on demand.** Its config stays in `tauri.conf.json` with
  `"create": false`, so its size and minimum size stay declarative; `dashboard::open` builds it
  with `WebviewWindowBuilder::from_config`. The roadmap's `app.windows: []` gives the same result
  with the config moved into code.
- **Every window is built from an async task.** Building a window in an event handler or a
  synchronous command deadlocks on Windows [docs: tauri 2.12.1 `WebviewWindowBuilder::new`]. The
  tray menu, the single-instance callback and the end of a lock are all handlers. A flag stops a
  second build while one is in flight.
- **Closing the dashboard** (close button, Alt+F4) destroys its webview. When the last window
  goes, Tauri raises `ExitRequested` with no exit code, and KeyClean prevents it, so it keeps
  running in the tray. An exit with a code (Quit, the close guard, an overlay close request) is never
  prevented. If the tray icon couldn't be created, closing the last window exits as before, so there
  is always a way to quit.
- **A manual launch opens the dashboard.** Starting minimized is M10 (§29).
- **A second launch** opens the dashboard of the running instance, or brings it to the front, and
  exits (invariant 12).
- **At idle with the dashboard closed there is no webview.** WebView2's processes exit with the
  last webview [assumption; harness S43].

### After a lock

The overlay is destroyed at `Unlocking`, as before (ADR 0014). Then:

| Dashboard when the lock was requested | Lock ended by                    | Result                      |
| ------------------------------------- | -------------------------------- | --------------------------- |
| open                                  | anything                         | dashboard back to the front |
| closed                                | an engine error, or overlay lost | dashboard opens (§46)       |
| closed                                | anything else                    | KeyClean stays in the tray  |

This amends ADR 0014's "the main window comes back to the front". Notifications are M10.

### `taskkill` without `/F`

- The tray icon adds a hidden top-level window (`tray_icon_app`, tray-icon 0.25.1). Its window
  procedure passes `WM_CLOSE` to `DefWindowProcW`, which would destroy it and leave a dead icon.
  It is registered with the exe's module handle, so the existing close guard matches it. The tray is
  built in `setup` before `guard_helper_windows`, both on the main thread, so the guard covers it.
- In M6, `taskkill` reached only one window (the overlay). If it reaches only the dashboard, closing
  to the tray would leave KeyClean running. The dashboard is subclassed too: the close button,
  Alt+F4 and the window menu send `WM_SYSCOMMAND` with `SC_CLOSE` first [docs: `WM_SYSCOMMAND`],
  `taskkill` sends a bare `WM_CLOSE` [assumption]. A bare `WM_CLOSE` exits the app.
- The dashboard's subclass is set on the main thread by enumerating its webview windows, once
  the window is built and again whenever it gains focus. Asking Tauri for the window's handle from
  a main-thread task reported it unavailable [tested: harness S44, 2026-10-12]. The task runs once
  WebView2 has started, about a second after the window first answers messages, so a bare
  `WM_CLOSE` in that first second leaves KeyClean in the tray instead of exiting [tested: S44 and
  S12 sent `taskkill` that early]. Nothing is locked then; known gap, like ADR 0014's
  sub-millisecond one for the overlay.

### Overlay close request

Kept from ADR 0014: a close request on the overlay ends the lock and exits KeyClean. The reason is
unchanged: `taskkill` may reach only the overlay, and ending only the lock would leave the app
running. Cost: Alt+F4 in a mouse-only lock quits instead of returning to the tray.

### Tray menu

| State       | Items                                                                                         |
| ----------- | --------------------------------------------------------------------------------------------- |
| Idle        | KeyClean, ● Ready, Lock keyboard, Lock selected devices, Open KeyClean, Settings, Quit        |
| Unavailable | as Idle, status "Engine unavailable - open KeyClean for details", the two lock items disabled |
| Problem     | as Idle, status "Something went wrong - open KeyClean for details"                            |
| Locked      | KeyClean, ● Cleaning - 01:42 (Locking…, Unlocking… around it), Unlock, Show overlay, Quit     |

- **Left click** opens the dashboard; **right click** shows the menu.
- **Locks from the tray** go through `overlay::lock`, the same overlay gate as the dashboard
  (invariant 11). Both use the remembered duration: "Lock keyboard" locks the keyboard only, "Lock
  selected devices" the remembered targets. Neither changes the remembered choices, because the
  item names what it locks.
- **Settings** opens the dashboard on its Settings tab: `index.html?tab=settings` for a new window,
  an `open-tab` event for an open one. No new command.
- **Show overlay** brings the overlay back to the front and focuses it (after Alt+Tab in a
  mouse-only lock, for example).
- **Quit** exits with a code; the exit ends any lock (`UserRequest`).
- **Updates:** the menu is rebuilt only when the state moves between idle and locked or the engine
  becomes available or not. During a lock, the status line and the tooltip change on each countdown
  status, which only arrives during a lock. Nothing runs at idle. The relay thread schedules the
  update on the main thread and never waits for it (invariant 3).
- **During a lock the tray is usually covered.** The overlay covers the whole monitor, taskbar
  included. The tray is reachable from another monitor's taskbar or with Win+B in a mouse-only
  lock. It is a secondary control; no exit depends on it.

### Errors with no window open

A lock request from the tray that fails before the engine is asked (the overlay didn't confirm,
for example) stores its error in the shared status, like an engine error. The tray then shows
"Something went wrong", and a dashboard opened later shows the plain-language error with its
technical details (§46). A request refused because a lock is already starting or running isn't
reported. The error clears when the next lock starts.

### Tray icon

- **Drawing:** Max's tray keycap (`docs/design/brand/tray-icon-draft.png`): a front view with a
  wider skirt, the top face cut out and an LED dot, traced as a vector. Idle is that shape in the
  taskbar's colour: dark for a light taskbar, white for a dark one. Locked is the same shape and
  dot in amber, with the top face still cut out (Max's decision, 2026-10-12), so colour is the only
  cue; the tooltip and menu say "Cleaning" too. Amber on a light taskbar has less contrast than
  on a dark one.
- **Files:** SVG sources in `assets/tray/`, rasterized by `scripts/tray-icons.mjs` with the dev
  dependency `@resvg/resvg-js` (Max's choice) to 16, 20, 24 and 32 px PNGs in
  `src-tauri/icons/tray/`, which are committed. `tauri::include_image!` decodes them at compile
  time, so no runtime image feature is needed.
- **Size:** the drawing that covers a 16 px icon at the primary monitor's scale.
- **Taskbar theme:** read from `SystemUsesLightTheme` (undocumented, see the research note). A
  subclass on the tray's hidden window re-reads it, and the scale, on each `WM_SETTINGCHANGE` or
  `WM_DISPLAYCHANGE` broadcast. No thread, no polling.
- **Feature:** Tauri's `tray-icon` feature. tray-icon and muda were already in `Cargo.lock`.

## Alternatives

- **`app.windows: []` and the window config in code.** Same behaviour; the config would move out
  of `tauri.conf.json`.
- **Hide the dashboard instead of destroying it.** Keeps WebView2 running at idle (ADR 0001,
  §30). Rejected.
- **Always bring the dashboard back after a lock.** A tray lock would end with a window popping up.
  Rejected; problems still open it.
- **An overlay close request ends only the lock.** `taskkill` could then leave the app running.
  Rejected.
- **Detect the theme change with `RegNotifyChangeKeyValue` on a waiting thread.** Works and is
  documented, but adds a thread; the broadcast reaches the tray's window anyway.
- **One icon for both taskbars.** Simpler, but an outline icon can't contrast with both.
- **A pre-created hidden overlay**, if a lock with no webview open is slow. Not needed unless the
  M8 measurement says so (research note); it would get its own ADR.

## Consequences

- At idle with the dashboard closed, KeyClean is the app process with its tray icon and the idle
  engine process, with no webview and no Raw Input registration in either.
- The first lock with no webview open starts WebView2 cold; harness S41 measures it with
  `--no-dashboard`.
- Quitting needs the tray (or `taskkill`); closing the window no longer exits.
- The harness ends the app with `taskkill /PID` (without `/F`) instead of closing its windows.
